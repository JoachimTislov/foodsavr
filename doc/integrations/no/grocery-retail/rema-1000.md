# Rema 1000 (Æ app)

Norwegian discount grocery chain. Its Æ app holds the loyalty membership, receipts, coupons and Scan & Pay. Per-transaction line items with EAN make it the best-fit purchase source. FoodSavr already has a client (`rema_client.dart`, see `specs/source-of-truth/integrations.md`).

## Access

- **api-private** — reverse-engineered REST API at `api.rema.no`. Login: OAuth 2.0 Authorization Code + PKCE at `id.rema.no`, with refresh tokens. Calls also need an API-management subscription header plus device and app-version headers (value deliberately not recorded; see the gist). Community-documented; may change without notice.
- **export** — GDPR subject-access endpoints exist in the app API (per gist); `remaquery` works from data pulled out of the app profile section.
- No official public developer API found.

## Data

- Transactions: list ("heads") and per-transaction rows; fields include date, store id/name, total, discount, receipt number, bonus.
- Line items: name, EAN/GTIN, internal product code, category, quantity, unit price, line amount, discount, applied offers.
- Also coupons (list/activate), stores (search, nearest), shopping lists (REST/WebSocket), article search and lookup by EAN.

## FoodSavr mapping

Purchases map directly to `LineItem` (EAN, name, qty, price). Coupons map to offer data. No expiry dates; quantity vs weight semantics unverified. Shopping-list sync possible, write access unverified.

## Risks and constraints

- Private API: ToS probably forbids third-party clients; relies on user consent (GDPR Art. 15) per `doc/plan/grocery-private-api-integration.md`.
- Subscription key and client id are extracted from the app binary and can be rotated or blocked.
- Per-user refresh tokens need secure storage.
