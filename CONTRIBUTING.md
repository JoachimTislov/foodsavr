Hey there! Thanks for your interest in helping out with FoodSavr. We're building this in the open and love getting input from the community.

This is a pretty casual project, but to keep things organized and ensure quality, we have a few guidelines.

## The Golden Rule: Small, Focused, Issue-Driven Changes

**We don't accept pull requests that aren't linked to an existing issue.**

Before you write any code, please check the [Issues tab](https://github.com/JoachimTislov/foodsavr/issues) to see if there's a relevant ticket. If not, open one! This lets us discuss the proposed change, agree on the approach, and make sure it aligns with the project's goals before you spend time on it.

The best contributions are small, focused, and solve one problem at a time.

## Our Workflow

1.  **Find or Create an Issue:** This is your starting point.
2.  **Fork the Repo:** Get your own copy of the project.
3.  **Create a Branch:** `git checkout -b feature/your-cool-idea` or `fix/that-annoying-bug`.
4.  **Write Code & Make Small Commits:** Do your thing!
5.  **Submit a Pull Request:** Link it to the issue you're solving.

## A Note on AI-Assisted Contributions

It's 2026, we know a lot of code is written with help from AI. That's awesome! We just ask that you stay in the driver's seat. To help us understand the context of your changes, please include the following in your Pull Request description:

*   **Author-By:** Your Name/Handle
*   **Model-Used:** (e.g., Gemini, Copilot, etc.)
*   **Summary:** A quick, concise summary of what you did.

We also love to see a brief **"Proof of Experience"**. This isn't about having a Ph.D. in computer science. It's just a sentence or two explaining why you're familiar with the area you're changing. For example:
> "I've worked with Flutter's `go_router` in a few other projects, so I have a good handle on the routing logic here."
or
> "I noticed this UI bug on my own device and have experience with responsive layouts in Flutter."

This helps us trust that the change is well-informed.

## Style & Structure

Consistency is key. Before submitting, make sure your code vibes with the rest of the project. Check out these guides:

*   **Code Style:** We follow [Effective Dart](https://dart.dev/effective-dart) guidelines.
*   **Folder Structure:** Take a look at how the `lib/` directory is organized by feature. We try to keep a clean separation between data, domain, and presentation layers.
