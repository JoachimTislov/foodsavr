# Audit: Modularity and Changeability — FoodSavr

**Date:** 2026-11-24  
**Scope:** `lib/`, `packages/`, `test/` of the FoodSavr app (audit only; no changes made)  
**Method:** structural reads of the layer map, dependency graphs, coding-standards and spec sources, and `flutter analyze` baselines

---

## 1. Summary

FoodSavr has a sound, documented layering: **views/widgets → services → interfaces → models/repositories**, with the pure-Dart `foodsavr_core` package kept separate. The data layer is well factored (repository pattern, injectable DI, interface-based). Main weaknesses:

- multiple widgets share files in the audited revision;
- the application layer couples controllers to concrete services;
- the feature-module catalog (ADR 0008) is spec-ahead: no app code reads it yet.

**Verdict:** strong on changeability of the data layer, moderate drift in the presentation layer, spec-ahead where the feature-module resolver is concerned.

## 3. Strengths (changeability that works)

1. **Layered structure** — coding-standards.md §Architecture and `specs/source-of-truth/architecture.md` document the 3-tier layout; `coding-standards.md` states rules: "Dependency Injection: GetIt service locator — never instantiate dependencies directly" (coding-standards.md:18).
2. **Repository Pattern with Interfaces** — `lib/interfaces/i_repository.dart`, `lib/interfaces/i_product_repository.dart`; Firestore implementations mark themselves as the interface: `lib/repositories/product_repository.dart:8` (`class ProductRepository implements IProductRepository`).
3. **DI graph is inverted at the data layer** — services depend on interfaces, repositories implement them and are singletons: `@LazySingleton(as: IProductRepository)`; module registration: `lib/register_module.dart`, `lib/di/validator_module.dart`, `lib/injection.dart` (`configureDependencies`).
4. **Pure-Dart core package** — `packages/foodsavr_core/lib/src/` (`line_item.dart`, `normalizer.dart`, `matcher.dart`, `shelf_life.dart`, `confidence_gate.dart`, `pipeline.dart`); boundary rule: "foodsavr_core is pure Dart, no Flutter or Firebase imports" (architecture.md:29).
5. **Tests mirror the layer map** — `test/controllers/`, `test/services/`, `test/repositories/`, `test/models/`, `test/views/`, `test/features/` …; `mocktail` is used to mock services in controller tests (`test/controllers/product_list_controller_test.dart:17-19`).
6. **Domain logic in models/services, not views** — e.g. `Product.isExpiringSoonWithin` (computed), `ProductService.addOrIncrementByBarcode`; coding-standards: "Business logic in models/services" (coding-standards.md:26, 41).

## 4. Findings (modularity & changeability)

### Finding 1 — One-widget-per-file convention drift (moderate)

`coding-standards.md:22` mandates "One widget per file: All widgets must be in their own file", and `:34`/`:63-64` forbid private widget builders in views. At `df1afafe`, the appendix query identified these files with multiple widget declarations.

- `lib/views/add_product_to_collection_view.dart` (2 widgets)
- `lib/views/collection_form_view.dart` (2 widgets)
- `lib/views/collection_list_view.dart` (2 widgets)
- `lib/views/product_form_view.dart` (2 widgets)
- `lib/views/profile_view.dart` (6 widgets)
- `lib/views/settings_view.dart` (4 widgets)
- `lib/widgets/common/app_navigation_rail.dart` (2 widgets)
- `lib/widgets/common/content_constraint.dart` (2 widgets)
- `lib/widgets/common/pwa_install_banner.dart` (3 widgets)

### Finding 2 — Concrete-class coupling in the application layer (moderate)

Controllers take concrete services: `ProductListController` holds `ProductService`/`CollectionService` (`lib/controllers/product_list_controller.dart:20-22`); `DashboardController` and `PreferencesController` also import concrete services. Interfaces exist for repositories, auth, validators and error reporters, so the data layer is well isolated — but services are not interface-based, so changing a service signature ripples through controllers and their tests.

### Finding 3 — Features live in two places; module catalog is spec-ahead (moderate)

Feature separation exists in `lib/features/third_party_integration/` while other features are folders in `lib/views/` (product, collection, auth, dashboard, transfer) + `lib/widgets/`. Separately, the ADR 0008 feature-module catalog is `specs/source-of-truth/registries/feature-modules.yaml` — its header says "Spec-ahead: no code reads this yet. The app will bundle this table so resolution works offline" and nothing in `lib/` or `packages/` reads it yet (grep-verified). The call-site rule "Feature call sites ask the module resolver, never a plan, a flag or RevenueCat directly" (architecture.md:31) is not implemented in code yet.

### Finding 4 — Dead code (low)

At `df1afafe`, the only reference to `GenericRepository` in `lib/`, `test/` and `packages/` was its declaration in `lib/utils/generic_repository.dart`. The file had been removed by `bf144b3`.

### Finding 5 — Environment/generated-code drift (baseline, not a code finding)

See §2: missing generated files block `flutter analyze` cleanly on `develop`, and the build_runner path is currently blocked by the go_router_builder SDK constraint.

---

## 5. Recommendations (direction, not fixes)

1. Separate the widgets listed in Finding 1.
2. Where a feature moves or gets replaced, start at the service level (add `IService`-style interfaces for controllers' inputs if the ripple is real), keeping repository interfaces as the primary seam.
3. Wire or prune the feature-module catalog per ADR 0008 before relying on it; the current split view/features/third_party_integration is the de-facto taxonomy.
4. Finding 4 was already addressed by the reviewed revision.
5. Regenerate `injection.config.dart` / `user_preferences_model.g.dart` (`make build`) and address the `go_router_builder` SDK pin so `make check` (analyze) can be green.
